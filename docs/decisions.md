2026-11-07 · Phase 3 · One `TransactWriteItems` per reservation: item 0 updates inventory (`stock = stock - 1` if `stock >= 1`), item 1 puts the `CONFIRMED` outcome (if `attribute_not_exists(requestId)`), both with `ReturnValuesOnConditionCheckFailure=ALL_OLD`. `SOLD_OUT` is a separate `PutItem` with the same `attribute_not_exists` condition · Stock and outcome change together or not at all, and no write ever overwrites an existing outcome, so a `CONFIRMED` can never become `SOLD_OUT`.
2026-11-07 · Phase 3 · `TransactionCanceledException` is classified by which item's condition failed: reservation `ConditionalCheckFailed` → duplicate (whatever the stock); inventory `ConditionalCheckFailed` with reservation `None` → out of stock (card missing if no old item, which is permanent); `TransactionConflict`/throttling → retryable; `ValidationError`/`ItemCollectionSizeLimitExceeded` → permanent; anything unexpected → retryable · Checking duplicate first means a repeated request is never turned into `SOLD_OUT`. Requiring the reservation reason to be `None` for sold out means a conflict on the reservation item (possibly a concurrent copy) retries rather than guessing. Retrying is always safe because the worker is idempotent. DynamoDB Local 3.3.2 reports both conditions as failed when a duplicate arrives after stock runs out, and the classifier treats that as a duplicate.
2026-11-07 · Phase 3 · Classification lives in `internal/storage` (DynamoDB specifics) and returns `reservations.ErrRetryable`/`ErrPermanent`/`ErrOutOfStock`; the processing rules (validate, reserve, sold out, bounded in-process retry of 3 attempts with 25–200 ms jitter) live in `internal/reservations`; `cmd/worker` only decodes, logs and reports failures · Same split as the API: business rules in `internal/`, thin handler. In-process retry absorbs short conflict bursts before spending an SQS receive.

2026-11-07 · Phase 3 · Hot-key tradeoff: worker timeout 10 s (one `WORKER_TIMEOUT` constant), queue visibility timeout 60 s (6×, derived from it), `maxReceiveCount` 5, batch size 10, event source max concurrency 5 · Every reservation for one card updates the same inventory item, so more concurrency mostly adds transaction conflicts rather than throughput. The headroom is for Phase 6 bursts on a single card; the cost is a slower queue drain under load and a poison message taking up to 5 × 60 s to reach the DLQ.
2026-11-07 · Phase 3 · The worker is deadline-aware: with less than 1.5 s left on the invocation it stops and reports the current and remaining records in `BatchItemFailures`; each record's DynamoDB calls get a context ending 1.5 s before the deadline · A timed-out invocation fails the whole batch and redelivers records that already succeeded; reporting the unprocessed ones keeps retries per record.

2026-11-07 · Phase 4 · The SPA signs in with authorization code + PKCE and keeps only the access token in `sessionStorage`, with no refresh token (expiry means signing in again); the code exchange is single-flight; a `404 RESERVATION_NOT_FOUND` means queued; polling is bounded (1, 2, 3, 5, 8, then 10 s steps within 60 s) and on timeout the UI shows Delayed, never Sold out; retries reuse one `requestId` per submission, which is saved as pending before the POST and resent on the next load (the server is idempotent per `requestId`), and pending entries expire after 10 minutes · An authorization code is redeemable once and StrictMode runs effects twice, so the exchange must not run twice; only the worker writes outcomes, so a 404 for a known `requestId` is "not processed yet", and a client timeout says nothing about stock, so it must not be shown as sold out. Saving the id before sending closes the gap where a refresh during an in-flight POST would lose it and a second click would create a second reservation. The 10-minute limit stops an old click from silently becoming a reservation.
