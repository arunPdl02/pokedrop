# Benchmark and acceptance results

Measured on `pokedrop-test`, 2026-11-10. This page records what was measured, under which limits, and
how to repeat it. Per-run reports are generated by `make drain-verify` into
`tests/load/results/<run>/report.json` (git-ignored); the tables below are copied from them.

## Headline

200 unique requests for 100 copies of one card, 2 in flight at a time, from a laptop to `us-west-2` (run `full-c2`):

| | |
|---|---|
| Outcome | **100 CONFIRMED + 100 SOLD_OUT**, final stock 0, no request ID with two rows, DLQ empty |
| Submit latency (n=200) | **p50 43.7 ms, p95 107 ms**, max 128 ms |
| Time to final outcome | **p95 under 1 s** (below the resolution of `updatedAt`); **max 60.0 s** for one request (see [the 60 s tail](#finding-2-one-conflicted-message-waits-a-full-minute)) |
| Submit throughput | 32.3 requests/s accepted |
| End-to-end throughput | 3.0 outcomes/s, held down by that one 60 s message |
| Queue drain time | 59.6 s after the last response, all of it that one message |
| Errors and throttles | 0 non-202, 0 API throttles, 0 worker throttles, 0 Lambda errors |

## Findings

### Finding 1: the account's Lambda limit decides how hard the test can push

The account allows 10 concurrent Lambda executions for the API and the worker together. The first sizing rule
was `limit - worker max - 1` = 4 in flight. At 4, run `full` still got **6 API throttles (HTTP 503) and 1 worker
throttle**, 2.2 to 2.7 s into the burst, not at cold start. The worker was probably at its peak by then, but that
was not verified. That run is kept above as
evidence and is not an acceptance run: 194 accepted requests cannot give 100 + 100.

The cause is not known. The cap now takes half the room (2 in flight, commit `671dcba`), and `full-c2` ran with no throttles. That
is an empirical margin, not a derived one. A higher account limit would allow a larger burst, but this benchmark
would then need to be repeated. A throttled worker invocation raises a message's receive count, so an oversized
test could also push valid messages to the DLQ; the invariants held in every run and nothing reached the DLQ.

### Finding 2: one conflicted message waits a full minute

In `full-c2`, one request lost a DynamoDB `TransactionConflict` on the hot inventory item on all 3 in-process
attempts, so the worker returned it to SQS. It was invisible for the 60 s visibility timeout, then succeeded on
attempt 2 as `SOLD_OUT`. That single message is the 60.0 s maximum, the 59.6 s drain and the low end-to-end
throughput. The worker's own log shows both deliveries (`attempt` 1 `RETRY`, `attempt` 2 `SOLD_OUT`).

This is the hot-key tradeoff in decision 29, measured: contention on one popular card is rare here (1 of 200) but
its cost is a whole visibility timeout, not a few milliseconds. It was not changed in Phase 6.

### Finding 3: time to final outcome cannot be measured below one second

The worker stores `updatedAt` in whole seconds, and the load generator's clock is only known to within a few
hundred milliseconds. Time to final outcome is `updatedAt - submit time`, so values under 1 s are not resolvable
and negative values are noise (the reports count them). Read these numbers as: **95% of requests reached a final
outcome within the resolution (about 1 s)**, plus the outliers above. A finer measure would need `updatedAt`
with sub-second precision, which was left out of scope.

## Reproduce

Prerequisites: AWS credentials for the `pokedrop` profile (`aws login`), `ALARM_EMAIL` exported, `TEST_USER_EMAIL`
and `TEST_USER_PASSWORD` in `.env.local`, k6 and Go installed. The local clock must be within 1 s of AWS's
(`make load` checks).

```sh
cd infra && npx cdk diff -c stage=test        # review, then:
make deploy STAGE=test

make seed STAGE=test STOCK=10
make test-integration STAGE=test              # rows 1, 2 and 5

make seed STAGE=test STOCK=10                 # small run
make load STAGE=test RUN=small REQUESTS=20 CONCURRENCY=2
make drain-verify STAGE=test RUN=small STOCK=10

make seed STAGE=test STOCK=100                # full run
make load STAGE=test RUN=full-c2 REQUESTS=200 CONCURRENCY=2
make drain-verify STAGE=test RUN=full-c2 STOCK=100

cd infra && npx cdk diff -c stage=test -c failAfterCommit=once   # review, then:
make fail-on STAGE=test MODE=once
make seed STAGE=test STOCK=10
make test-integration-failure STAGE=test      # row 3

make destroy STAGE=test
```

Always reseed (`make seed STOCK=...`) before a run: `drain-verify` checks final stock against the seeded value
and fails if they disagree. `make load` refuses a concurrency above what the account's Lambda limit allows; on a
different account the cap, and so the numbers, will differ. Keep failure injection off for timing runs: it fails
every first delivery and retries it 60 s later.

## Limits of this benchmark

- One card, one trainer, a handful of seconds of load, and a closed model (each virtual user waits for its
  response). It shows correctness under contention and the shape of the latency, not a capacity limit.
- The account's concurrency limit of 10 keeps the burst small. The numbers describe this account.
- Submit latency includes the laptop's network path to `us-west-2`.
- Time to final outcome is limited to about 1 s resolution (Finding 3).
- Lambda counts come from CloudWatch minute buckets starting at the minute of the first request.
- A single acceptance run was recorded; the 60 s tail is one observed conflict, not a measured rate.
